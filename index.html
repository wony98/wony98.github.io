경기 데이터 분석·예측 시스템 연구

경기 전 자료로 승패와 총득점을 예측하고, 경기 후 실제 플레이 기록과 대조해 오류를 찾은 개인 연구입니다. 통계 모델과 선수별 경기 내용을 읽는 LLM 네레이터를 함께 실험했습니다.

기간2026.03–09형태개인 연구 / 연구 종료

사용 도구JSONLLightGBMLLMPython / pandas

어떤 문제에서 시작했나요?

경기 전 기록으로 승패와 총득점을 예측할 때, 선수별 경기 내용을 읽는 LLM이 통계 모델의 판단을 보완할 수 있는지 알아보려 했습니다. 예측이 빗나간 원인을 추적할 수 있도록 당시의 입력 자료와 판단 근거를 함께 남겼습니다.

어떻게 만들었나요?

공식 경기·투구·타구 자료와 경기 환경을 경기·선수 ID로 연결하고, 경기 전 시점에 사용할 수 있는 입력을 구성했습니다. Logistic Regression, XGBoost, LightGBM을 비교했고 후기 모델은 승패 분류와 총득점 회귀로 나눴습니다.

LLM 네레이터는 경기별 자료에서 양 팀의 근거와 반론을 비교하도록 구성했습니다. 긴 입력에서 근거가 묻히는 문제에 대응해 경기별 분리와 섹션별 메모를 시험했습니다. 경기 종료 후에는 저장한 판단을 실제 플레이 기록(PBP)과 박스스코어에 대조했습니다.

판정 방식 비교와 확장 여부 결정

같은 근거를 두 LLM이 읽은 결과를 비교했습니다. 일치도가 기준에 못 미친 판정 방식은 확장하지 않기로 했습니다.

프로젝트 결과

예측 당시 입력과 경기 후 자료를 구분해 오류를 조사할 수 있게 했습니다. 다만 서로 충돌하는 근거를 종합해 새 경기의 승리 팀을 일관되게 판단하는 기준은 해결하지 못했습니다.

종료 후 재실험에서 기존 누수 판정 규칙으로 선별한 피처 세트를 같은 분할에서 비교하고 실행 설정과 결과를 MLflow로 추적했습니다. 규칙 탐지 열을 뺀 모델은 이 분할에서 시장가격 환산 확률과 같은 수준(test AUC 0.58)이었습니다.

경기별 메모장과 독립 추론

여러 경기를 한 번에 판단하던 입력을 나눴습니다. 한 경기의 사실과 참고 사례를 메모장으로 묶고, 경기마다 따로 분석하게 했습니다.

추가로 시험한 방법

핵심 근거를 앞부분에 재배치

충돌하는 근거를 입력 앞에 다시 배치해 비교했습니다. 적중 건수가 늘지 않아 기본 적용은 보류했습니다.

분야별 중간 판단 저장

선발·타선·불펜 등 10개 섹션을 차례로 읽고, 근거와 반론을 JSON으로 저장했습니다. 최종 단계가 이 기록을 다시 읽고 비교하도록 시험했습니다.

입력에서 빠진 자료와 판단 기록에서 빠진 근거를 나눠 확인할 수 있게 됐습니다. 근거 ID의 기록 여부는 검사했지만, 그 의미를 정확히 이해하고 판단에 반영했는지는 별도 문제로 남았습니다.

어떤 근거를 우선해 판단할 것인가

사전자료를 전달해도 종합 성적에 치우치거나, 근거가 부족하다며 판단을 과도하게 보류했습니다. 과거 경기에서 판단 방법을 뽑아 참고 사례로 연결했고, 다음 연구에서는 조건과 반론을 더 자세히 기록했습니다.

  1. 기준 추출 연구

    과거 경기에서 판단 방법 정리

    실제 플레이와 당시 사전정보를 대조했습니다. 어떤 조건을 함께 봐야 했는지, 어떤 반대 근거가 그 판단을 무효화하는지 남겼습니다. 경기 후에야 알게 된 사건은 사전 조건에서 제외했습니다.

  2. 검색 연구

    다른 경기의 당일 조건과 연결

    대상 경기보다 이전 사례만 검색했습니다. 과거 선수의 수치나 근거 번호를 그대로 쓰지 않고, 오늘 경기에서 대응하는 값과 출처에 다시 연결했습니다.

  3. 단계별 판정 실험

    양 팀의 승리 경로와 반론 비교

    필수조건 충족 여부와 기준을 무효화하는 조건을 따로 판단했습니다. 양 팀의 승리 경로, 서로 충돌하는 근거, 최종 선택 이유를 단계별로 저장했습니다.

판단기준 추출·검색·단계별 판정은 각각 별도 연구로 진행했습니다.

참고 기준을 찾았는지뿐 아니라, 오늘 경기에서 그 기준을 적용하거나 배제한 이유까지 추적할 수 있게 했습니다.

어떤 문제에서 시작했나요?

입찰을 검토할 때는 문서마다 예산, 일정, 제출서류를 찾아야 합니다. 여러 사업을 비교하면 서로 다른 문서의 조건을 함께 확인해야 하므로, 질문에서 필요한 본문을 찾아 근거와 함께 답하는 기능을 만들었습니다.

어떻게 만들었나요?

팀은 공공 RFP 100건(HWP 95건, PDF 5건)을 정제하고, embeddinggemma-300m과 Chroma로 본문과 표의 색인을 분리했습니다.

의미 기반 검색(Dense)과 BM25/Kiwi 키워드 검색을 RRF로 결합했습니다. 여러 문서를 비교하는 질문에서는 한 문서에 근거가 쏠리지 않도록 문서 범위와 후보 배치를 조정했습니다.

답변 생성에는 질문 유형에 따라 GPT-5 mini, MiniMax-M3, Nemotron-3-Ultra를 선택하도록 구성했습니다. 프롬프트에 근거와 출처 규칙을 두고, 확정값은 템플릿으로 처리하며 모호한 질문은 문서 후보를 되묻게 했습니다.

검색(Retrieval)과 답변용 근거 구성을 맡았습니다. 문서 범위 지정, 하이브리드 검색, 다중문서 후보 배치와 출처 정규화를 구현하고, 팀과 원문을 대조해 평가셋을 다시 검수하는 과정을 주도했습니다.

질문에 맞는 검색 범위

기관명과 사업명, 문서 ID로 범위를 좁혔습니다. 예산이나 제출서류처럼 질문 유형에 맞는 섹션을 후보로 모았습니다.

두 검색 결과 결합

문장 의미를 비교하는 Dense 검색과 키워드 중심의 BM25/Kiwi 검색을 함께 썼습니다. 두 검색의 순위는 RRF 방식으로 합쳤습니다.

출처 정보 정규화

문서·청크 ID와 출처를 기존 메타데이터와 매핑에서 채웠습니다. 찾지 못한 ID는 지어내지 않고 빈 값으로 남겨, 필수 필드 오류로 기록했습니다.

검색 평가와 원문 검수

문서를 못 찾은 경우와 근거 표기가 달라 실패한 경우를 나눠 살폈습니다. 원문을 클릭해 대조할 수 있는 검수 도구도 마련했습니다.

프로젝트 결과

문서 보관함, 채팅 이력과 모델 자동 선택을 통합해 단일문서 질문과 다중문서 비교를 지원했습니다. 검색 고도화 후 동일한 내부 비교형 40문항에서 두 문서가 상위 20개 후보에 함께 포함된 결과는 39/40에서 40/40으로 늘었습니다. 최종 답변 정확도와는 별도 지표입니다.

전달 계약과 설계 목표

  • 함께 넘기는 정보 9항목: contexts, evidence_units, doc_id, chunk_id, source_file, source_rank, doc_scope, active_doc_ids, metadata_answer
  • 설계 문서의 검증 목표 6항목: query 존재 / contexts 또는 evidence_units 존재 / doc_id·chunk_id·source_file 일관성 / 단일문서 문서 범위 / 다중문서 문서 수 / metadata direct answer 필드·값 존재

설계 6항목과 공개 구현의 차이

공개 validator는 필수 키와 자료형, 근거 필드의 누락을 검사합니다. 검색 결과가 있을 때는 근거가 참조한 순위도 확인합니다. 오류가 있으면 valid=false, 다중문서 수 부족은 경고로 기록합니다.

contexts는 빈 목록을 허용하고 evidence_units는 선택 항목입니다. 이 validator가 ID와 원문의 일치, 단일문서 범위, metadata_answer의 필드·값 유효성을 보장하지는 않습니다.

번들 생성 도구는 검증 옵션을 켰을 때 결과를 첨부합니다. 별도 오류 종료 옵션을 함께 켜면 산출물을 저장한 뒤, 검증 오류가 있을 때 오류 상태로 종료합니다.

기간2026.04–05인원5명

사용 도구AlbumentationsMMDetectionPyTorchRTMDet

어떤 문제에서 시작했나요?

포장 없이 알약만 남아 있으면 사진 속 모양과 각인으로 약품명을 찾아야 합니다. 손바닥 사진은 촬영용 흰 배경 사진과 조건이 달라, 위치를 찾더라도 약품명을 틀리거나 손가락을 알약으로 인식하는 문제가 있었습니다.

어떻게 만들었나요?

팀은 학습 데이터를 정제하고 다양한 배경의 합성 사진을 만들었습니다. 탐지 후보를 비교해 RTMDet-tiny를 선택하고, 잘라낸 알약 이미지를 EfficientNet-B0로 재분류했습니다.

OCR의 각인 인식 한계에 대응해 Qwen2.5-VL-3B가 API 후보 각인 중 하나 또는 UNKNOWN을 고르도록 제한했습니다. 식약처 API·캐시와 색상·모양을 함께 확인하고, 약품 후보와 추가 확인 상태를 Gradio 데모에 표시했습니다.

손가락을 알약으로 잘못 찾는 문제

문제
흰 배경 알약 사진에서 탐지 성적이 높았던 모델도 손바닥 사진에서는 약품명을 틀리거나 손가락을 알약으로 찾았습니다.
관찰
합성 사진 중 알약 1개 비중은 3.4%, 평가 사진은 약 60.6%가 1개였습니다. 손가락 끝을 알약으로 오인했습니다.
조치
팀 합성 스크립트에 기반해 알약 개수·크기·배치와 학습 조건을 바꾸고, 같은 평가셋에서 비교했습니다.
결과
같은 평가셋에서 v4가 기준 모델보다 더 많은 박스를 맞혔습니다.여러 설정을 함께 바꿔 어느 변경이 얼마나 영향을 줬는지는 분리하지 못했습니다.

confidence 임계값 선택

문제
오탐을 줄이려 임계값을 올리면 맞힌 박스도 함께 사라질 수 있었습니다.
조치
같은 v4 저장 예측을 confidence별로 필터링하고, 동일한 IoU 매칭 규칙으로 비교했습니다.
결과
0.05에서 정답 22/47·미매칭 박스 84, 0.25에서 22/47·10, 0.30에서는 21/47·7로 정답도 줄었습니다.
선택
v4 실험 설정에서는 정답 수를 유지한 0.25를 선택했습니다.
